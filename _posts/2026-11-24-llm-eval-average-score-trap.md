## 평균 점수만 보고 모델을 바꿔도 될까

LLM을 쓰는 서비스를 운영하다 보면 "새 모델로 바꿀까?", "이 프롬프트가 더 나은가?"를 자주 결정해야 합니다. 보통은 평가 세트(eval)를 돌려 **평균 점수**를 비교합니다. 정답률 89.7%와 92.7%가 나오면 92.7% 쪽으로 바꾸는 식입니다.

그런데 평균 하나에는 두 가지 함정이 숨어 있습니다. 문제가 너무 쉬워 점수가 위쪽에 몰리는 **천장 효과(ceiling effect)**, 그리고 평균은 올랐는데 가끔 나오는 아주 나쁜 답이 늘어난 **실패 꼬리(failure tail)**입니다. 이 글은 이 두 함정을 가상 데이터로 직접 재현하고, 교체를 결정하기 전에 함께 봐야 할 지표를 정리합니다.

<!--more-->

글에 나오는 모델 A·B와 모든 숫자는 설명을 위해 만든 **가상 데이터**입니다. 실제 모델이나 서비스의 결과가 아닙니다. 실험 코드는 파이썬 표준 라이브러리만 쓰므로 그대로 복사해 돌려 볼 수 있습니다. 통계 방법은 Anthropic이 2024년 11월 공개한 글과 논문 "Adding Error Bars to Evals"를 주로 참고했습니다.

## 1. 왜 평가 결과를 의심해야 하나

OpenAI의 평가 가이드는 생성형 AI의 출력이 **같은 입력에도 매번 달라질 수 있다**는 점을 먼저 짚습니다. 그래서 전통적인 소프트웨어 테스트처럼 "통과/실패"만으로는 부족하다고 설명합니다.

Anthropic의 글은 한 걸음 더 나아가, 평가 문제를 **더 큰 문제 집단에서 뽑은 표본**으로 보자고 제안합니다. 표본이라면 점수에는 우연에 따른 흔들림이 있습니다. 그러니 점수 옆에 **표준오차(standard error)**를 함께 적어야 한다는 것이 첫 번째 권고입니다.

정리하면 평가 점수는 "정확한 측정값"이 아니라 "흔들리는 추정값"입니다. 이 전제를 받아들이면 아래 함정들이 잘 보입니다.

## 2. 함정 하나: 천장 효과

### 천장 효과란

천장 효과는 측정 도구의 최댓값 근처에 점수가 몰려서, 그 위쪽의 차이를 더는 구별하지 못하는 현상입니다. 다섯 단어만 외우게 하는 기억력 시험이라면 대부분 만점이라 기억력 좋은 사람끼리 차이를 알 수 없는 것과 같습니다.

LLM 평가에서는 **평가 세트 대부분이 요즘 모델에게 너무 쉬운 경우**가 여기에 해당합니다. 쉬운 문제는 두 모델 모두 맞히므로 비교에 아무 정보도 주지 않습니다. 결국 차이를 만드는 건 소수의 어려운 문제인데, 평균에서는 그 차이가 희석됩니다.

### 가상 실험

쉬운 문제 270개와 어려운 문제 30개, 모두 300문제로 된 평가 세트를 가정했습니다. 모델 A와 B는 쉬운 문제를 둘 다 98% 확률로 맞히고, 어려운 문제는 A가 30%, B가 60% 확률로 맞히도록 설정했습니다. 한 번 돌린 결과는 다음과 같습니다.

| 모델 | 전체 정답률 | 표준오차 | 쉬운 문제 | 어려운 문제 |
|---|---|---|---|---|
| A | 89.7% | 1.8%p | 96.7% | 26.7% |
| B | 92.7% | 1.5%p | 98.1% | 43.3% |

전체 평균만 보면 3%p 차이입니다. 그런데 B−A 차이의 95% 신뢰구간을 계산하면 **−0.6%p ~ 6.6%p**로 0을 포함합니다. 이 평가 세트만으로는 "B가 낫다"고 말하기 어렵다는 뜻입니다.

반면 어려운 문제만 떼어 보면 26.7%와 43.3%로 차이가 확연합니다. 30문제라 이것도 흔들림이 크지만, 적어도 **어디를 더 보강해야 하는지**는 알려 줍니다. 쉬운 270문제는 두 모델을 가르는 데 거의 쓸모가 없었습니다.

### 대처법

- **난이도별로 나눠서 보기:** 전체 평균과 함께 어려운 문제 구간의 점수를 따로 적습니다.
- **너무 쉬운 문제 정리:** 후보 모델들이 모두 맞히는 문제는 비교용 세트에서 줄이고, 회귀 확인용으로 따로 둡니다.
- **실제 사용 분포 반영:** Anthropic 문서는 평가를 **실제 작업 분포를 닮게** 만들라고 권하고, OpenAI 가이드도 운영 데이터와 예외 상황(edge case)을 평가 세트에 넣으라고 합니다. 운영 로그에서 실패했던 입력을 모아 추가하면 천장에서 내려올 수 있습니다.

## 3. 짝지어 비교하면 오차가 줄어든다

같은 문제를 두 모델에 모두 풀게 했다면, 문제마다 **B 점수 − A 점수**를 계산해 그 평균과 표준오차를 보는 편이 낫습니다. Anthropic은 이를 짝지은 차이(paired difference) 분석이라 부르며, 추가 비용 없이 오차를 줄이는 방법이라고 설명합니다. 모델들은 대체로 같은 문제에서 함께 맞히거나 함께 틀리기 때문입니다.

위 실험에서도 두 모델의 표준오차를 따로 합쳐 계산하면 2.3%p였지만, 짝지어 계산하면 1.9%p로 줄었습니다. 같은 데이터로 더 좁은 신뢰구간을 얻은 셈입니다.

Anthropic 글은 이 밖에도 몇 가지를 권합니다.

- **군집 표준오차:** 지문 하나에 질문 여러 개가 붙는 독해 평가처럼 문제끼리 독립이 아니면, 지문 단위로 묶어 오차를 계산합니다. 이렇게 계산한 오차가 단순 계산보다 세 배 넘게 큰 경우도 있었다고 합니다.
- **같은 문제 여러 번 돌리기:** 생각 과정(chain-of-thought)을 쓰는 경우, 한 문제의 답을 여러 번 뽑아 평균을 내면 문제 안의 흔들림을 줄일 수 있습니다.
- **검정력 분석:** "3%p 차이를 잡아내고 싶다"처럼 목표를 정하면, 필요한 문제 수를 미리 계산할 수 있습니다.

## 4. 함정 둘: 실패 꼬리

### 평균이 올랐는데 사고는 늘었다

이번에는 정답/오답이 아니라 **1~5점 채점**을 가정했습니다. 요약 품질이나 상담 답변처럼 LLM 판정자(LLM-as-a-judge)나 사람이 점수를 매기는 경우입니다. 응답 500건을 채점한 가상 결과는 다음과 같습니다.

| 지표 | 모델 A | 모델 B |
|---|---|---|
| 평균 점수 | 3.99 | 4.28 |
| 5점 비율 | 19.8% | 59.8% |
| 2점 이하 비율 | 1.8% | 9.4% |
| 1점 비율 | 0.6% | 6.8% |
| 하위 5% 평균 | 2.52 | 1.00 |

평균만 보면 B가 확실히 좋아 보입니다. 5점짜리 훌륭한 답도 세 배 많습니다. 하지만 1점, 즉 **쓸 수 없는 답**이 A는 500건 중 3건, B는 34건입니다. 하위 5%만 모아 보면 B는 전부 1점입니다.

서비스 입장에서는 이 차이가 클 수 있습니다. 사용자는 평균을 경험하지 않고 **자기가 받은 답 하나**를 경험합니다. 1점짜리 답이 틀린 금액 안내나 엉뚱한 정책 설명이라면, 평균이 0.3점 오른 것으로는 상쇄되지 않습니다.

### 대처법

- **분포를 같이 보기:** 평균 옆에 점수별 비율이나 히스토그램을 둡니다.
- **꼬리 지표를 따로 정하기:** "2점 이하 비율", "하위 5% 평균"처럼 나쁜 쪽을 재는 지표를 정하고, 교체 조건에 넣습니다.
- **실패 사례 직접 읽기:** 숫자만 보지 말고 1~2점 답을 열어 봅니다. 같은 유형이 반복되는지 확인하면 프롬프트로 막을 수 있는지도 보입니다.
- **판정자 점검:** OpenAI 가이드는 자동 채점을 사람 판단으로 보정하라고 권합니다. LLM 판정자를 쓴다면 일부 표본을 사람이 다시 채점해 일치하는지 확인합니다.

## 5. 실험 코드

아래 코드로 위 두 실험을 재현할 수 있습니다. 시드(seed)를 고정해 두었으므로 같은 파이썬 버전에서는 같은 숫자가 나옵니다. 글의 숫자는 Python 3.14에서 돌린 결과입니다.

```python
import math, random, statistics as st

random.seed(42)

def mean_se(xs):
    return st.mean(xs), st.stdev(xs) / math.sqrt(len(xs))

# 1. 천장 효과: 쉬운 270문제(둘 다 98%) + 어려운 30문제(A 30%, B 60%)
qs = [("easy", 0.98, 0.98)] * 270 + [("hard", 0.30, 0.60)] * 30
a1, b1, kind = [], [], []
for k, pa, pb in qs:
    a1.append(1 if random.random() < pa else 0)
    b1.append(1 if random.random() < pb else 0)
    kind.append(k)

d = [b - a for a, b in zip(a1, b1)]          # 문제별 짝지은 차이
md, sed = mean_se(d)
print(f"B-A {md*100:.1f}%p, 95% 구간 {(md-1.96*sed)*100:.1f} ~ {(md+1.96*sed)*100:.1f}%p")

# 2. 실패 꼬리: 1~5점 채점 500건
def draw(w):
    return random.choices([1, 2, 3, 4, 5], weights=w)[0]

a2 = [draw([1, 2, 17, 60, 20]) for _ in range(500)]
b2 = [draw([7, 2, 6, 25, 60]) for _ in range(500)]
for name, xs in (("A", a2), ("B", b2)):
    low = sum(x <= 2 for x in xs) / len(xs)
    worst = sorted(xs)[: len(xs) // 20]      # 하위 5%
    print(f"{name}: 평균 {st.mean(xs):.2f}, 2점 이하 {low*100:.1f}%, 하위 5% 평균 {st.mean(worst):.2f}")
```

가중치를 바꿔 가며 돌려 보면, 평균은 거의 같은데 꼬리만 다른 경우나 평균이 낮아도 꼬리가 짧은 경우를 쉽게 만들 수 있습니다.

## 6. 모델·프롬프트 교체 전 점검표

위 내용을 교체 결정에 쓸 수 있게 정리하면 다음과 같습니다. 팀 상황에 맞게 기준값을 정해 쓰면 됩니다.

| 확인할 것 | 질문 |
|---|---|
| 불확실성 | 점수 옆에 표준오차나 신뢰구간을 적었나? 차이의 구간이 0을 포함하지 않나? |
| 비교 방식 | 같은 문제로 짝지어 비교했나? |
| 문제 수 | 잡아내고 싶은 차이에 비해 문제가 충분한가? |
| 천장 효과 | 후보 모두 다 맞히는 문제가 대부분이지 않나? 어려운 구간 점수는? |
| 실패 꼬리 | 최저 점수 비율과 하위 구간 평균이 나빠지지 않았나? |
| 실제 분포 | 운영에서 실제로 들어오는 입력과 예외 상황이 들어 있나? |
| 판정자 | 자동 채점 결과를 사람이 일부 확인했나? |

OpenAI 가이드는 피해야 할 방식으로 "잘 되는 것 같다"는 느낌에 기대는 평가를 꼽습니다. 그리고 변경할 때마다 평가를 다시 돌리고, 새로 발견한 실패 사례를 평가 세트에 계속 더하라고 권합니다. 위 점검표도 한 번 쓰고 끝내기보다 교체할 때마다 반복하는 편이 좋습니다.

참고로 OpenAI는 자사 Evals 플랫폼을 종료한다고 공지했습니다(2026년 11월 30일 종료 예정). 이 글에서 인용한 평가 원칙은 특정 플랫폼과 무관하게 쓸 수 있는 내용입니다.

## 마무리

- 평가 점수는 표본에서 나온 **흔들리는 추정값**입니다. 표준오차와 신뢰구간을 함께 적습니다.
- 같은 문제로 **짝지어 비교**하면 추가 비용 없이 오차가 줄어듭니다.
- 쉬운 문제가 대부분이면 **천장 효과**로 차이가 희석됩니다. 어려운 구간을 따로 봅니다.
- 평균이 올라도 **실패 꼬리**가 길어질 수 있습니다. 최저 점수 비율과 하위 구간 평균을 교체 조건에 넣습니다.
- 숫자와 함께 **실패한 답을 직접 읽습니다.**
