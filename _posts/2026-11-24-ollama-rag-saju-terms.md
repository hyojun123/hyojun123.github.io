## 모델이 모르는 내용을 문서로 알려 주기

[1편](/2026/11/24/ollama-local-llm-start/)에서 `gemma3:1b`에게 노벨 문학상 수상자를 물었더니 없는 이름을 지어냈습니다. 작은 모델은 모르는 것을 모른다고 하지 않고 그럴듯하게 꾸며 냅니다. 이럴 때 쓰는 방법이 **RAG(검색 증강 생성)**입니다. 질문과 관련된 문서를 먼저 찾아서, 그 문서를 질문과 함께 모델에 넘기는 방식입니다.

이 글은 초보자용 로컬 LLM 시리즈의 2편입니다. 사주팔자 용어(천간·지지·오행)를 정리한 짧은 문서를 만들고, 100줄이 안 되는 파이썬 코드로 "문서를 근거로 답하는 AI"를 만들어 봅니다. 벡터 DB나 프레임워크 없이 Ollama와 파이썬만 씁니다.

미리 밝혀 둡니다. 사주풀이는 전통문화이자 재미로 보는 콘텐츠이고 과학적 근거가 없습니다. 이 글의 예제는 **용어의 뜻을 찾아 주는 것**이지 운세를 맞히는 모델이 아닙니다. 진학, 취업, 투자 같은 중요한 결정에 사주를 쓰면 안 됩니다.

<!--more-->

글의 실행 결과는 Apple M4 Pro(메모리 48GB) Mac, Ollama 0.40.16, 생성 모델 `gemma3:1b`, 임베딩 모델 `nomic-embed-text`, 파이썬 3.14와 `ollama` 라이브러리 0.6.3으로 직접 돌려 본 것입니다. 답변과 점수, 속도는 환경과 버전에 따라 달라질 수 있습니다.

## 1. RAG가 뭔가요

RAG는 2020년 Lewis 등이 발표한 논문 「Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks」에서 나온 이름입니다. 논문은 모델 안에 학습된 기억(parametric memory)과 바깥에서 검색해 오는 기억(non-parametric memory)을 합쳐 글을 생성하는 모델을 RAG라고 불렀습니다. 요즘은 더 넓게, "검색한 문서를 프롬프트에 넣어 답하게 하는 방식"을 통틀어 RAG라고 부릅니다.

흐름은 세 단계입니다.

| 단계 | 하는 일 | 이 글에서 쓰는 것 |
|---|---|---|
| 1. 준비 | 문서를 조각으로 나누고, 조각마다 임베딩(숫자 벡터)을 만들어 둠 | `nomic-embed-text` |
| 2. 검색 | 질문도 임베딩으로 바꿔, 가장 비슷한 조각을 고름 | 코사인 유사도 |
| 3. 생성 | 고른 조각과 질문을 함께 모델에 넘겨 답을 받음 | `gemma3:1b` |

**임베딩**은 글을 숫자 목록(벡터)으로 바꾼 것입니다. 뜻이 비슷한 글은 벡터도 비슷한 방향을 가리키도록 학습된 모델이 만들어 줍니다. 그래서 질문 벡터와 방향이 가장 비슷한 문서 조각을 찾으면, 낱말이 똑같지 않아도 관련 있는 내용을 찾을 수 있다는 것이 기본 생각입니다.

## 2. 준비하기

1편에서 Ollama와 `gemma3:1b`를 설치했다면 임베딩 모델만 더 받으면 됩니다.

```bash
ollama pull nomic-embed-text
pip install ollama
```

`nomic-embed-text`는 Ollama 라이브러리 기준 274MB짜리 임베딩 전용 모델입니다. 모델 페이지는 "임베딩을 만드는 데만 쓸 수 있는 모델"이라고 설명합니다. `ollama show nomic-embed-text`로 확인하면 매개변수 약 1억 3,700만 개, 벡터 길이 768, 라이선스 Apache License 2.0이 나옵니다.

임베딩이 잘 만들어지는지부터 확인합니다. Ollama의 임베딩 API는 `POST /api/embed`이고, `model`과 `input`을 보냅니다.

```bash
curl http://localhost:11434/api/embed -d '{
  "model": "nomic-embed-text",
  "input": "search_query: 천간은 무엇인가요?"
}'
```

응답의 `embeddings`에 벡터가 들어 있습니다. 제 환경에서는 숫자 768개짜리 벡터 하나가 왔고, `prompt_eval_count`(입력 토큰 수)는 15, `total_duration`은 약 0.03초였습니다. `input`에 문자열 배열을 넣으면 여러 글을 한 번에 임베딩할 수 있습니다.

## 3. 문서 만들기

예제 문서는 제가 직접 쓴 사주 용어집입니다. 내용은 한국민족문화대백과사전의 「사주」, 「간지」, 「오행론」, 「음양오행설」 항목에서 확인한 것만 넣었습니다. `docs/saju-terms.md`로 저장하고, `# 제목` 한 줄과 설명 2~3문장을 한 조각으로 삼았습니다. 모두 13조각입니다.

```markdown
# 천간
천간은 갑, 을, 병, 정, 무, 기, 경, 신, 임, 계의 10가지다. 10가지라서 십간이라고도 한다.

# 팔자
사주의 네 기둥은 각각 간지 두 글자로 적는다. 두 글자씩 네 기둥이라 모두 여덟 글자가 되므로 팔자(八字)라고도 한다. 그래서 흔히 사주팔자라고 붙여 부른다.

# 오행의 상생
상생은 오행이 서로 낳는 관계다. 목은 화를 낳고, 화는 토를 낳고, 토는 금을 낳고, 금은 수를 낳고, 수는 목을 낳는다.

# 오행과 방위, 계절
방위로는 동쪽이 목, 서쪽이 금, 남쪽이 화, 북쪽이 수, 중앙이 토에 배정된다. 계절로는 봄이 목, 여름이 화, 가을이 금, 겨울이 수에 배치된다.

# 읽을 때 주의할 점
사주풀이는 전통문화이자 재미로 보는 콘텐츠이며 과학적 근거가 없다. 진학, 취업, 결혼, 투자, 건강 같은 중요한 결정을 사주에 맡겨서는 안 된다. 이 문서는 용어의 뜻만 설명한다.
```

나머지 조각의 제목은 사주, 간지, 지지, 육십갑자, 오행, 오행의 상승(상극), 연주와 입춘, 월주와 절기·일주입니다. 문서를 조각으로 나누는 일을 흔히 **청킹(chunking)**이라고 부릅니다. 이 예제에서는 한 조각에 용어 하나만 담기도록 나눴습니다.

## 4. 코드 따라 쓰기

`rag.py` 하나에 전부 들어갑니다. 먼저 문서를 조각으로 나누고 임베딩을 만드는 부분입니다.

```python
import ollama
from pathlib import Path

EMBED_MODEL = "nomic-embed-text"
CHAT_MODEL = "gemma3:1b"
TOP_K = 3


def load_chunks(path):
    """'# 제목' 줄을 기준으로 문서를 조각으로 나눈다."""
    chunks = []
    for block in path.read_text(encoding="utf-8").split("\n# "):
        block = block.lstrip("# ").strip()
        if block:
            title, _, body = block.partition("\n")
            chunks.append({"title": title.strip(), "text": body.strip()})
    return chunks


def embed(texts, prefix):
    """nomic-embed-text는 용도를 알려 주는 접두어를 붙여서 임베딩한다."""
    res = ollama.embed(model=EMBED_MODEL, input=[prefix + t for t in texts])
    return res["embeddings"]
```

`prefix`가 눈에 띌 겁니다. Nomic의 모델 카드는 입력 글에 **작업 접두어를 반드시 붙이라**고 안내합니다. RAG라면 문서에는 `search_document: `, 질문에는 `search_query: `를 붙입니다. 모델마다 이런 규칙이 다르므로, 임베딩 모델을 바꿀 때는 그 모델의 카드를 먼저 읽어야 합니다.

다음은 검색입니다. 질문 벡터와 각 조각 벡터의 **코사인 유사도**를 구해 높은 순으로 3개를 고릅니다.

```python
def cosine(a, b):
    dot = sum(x * y for x, y in zip(a, b))
    na = sum(x * x for x in a) ** 0.5
    nb = sum(y * y for y in b) ** 0.5
    return dot / (na * nb)


def search(question, chunks, vectors):
    q = embed([question], "search_query: ")[0]
    scored = [(cosine(q, v), c) for v, c in zip(vectors, chunks)]
    scored.sort(key=lambda s: s[0], reverse=True)
    return scored[:TOP_K]
```

Ollama 문서는 `/api/embed`가 길이 1로 정규화된 벡터를 돌려준다고 설명하고, 의미 검색에는 코사인 유사도를 쓰라고 권합니다. 실제로 받은 벡터의 길이를 계산해 보니 0.9999999였습니다. 조각이 13개뿐이라 벡터 DB 없이 파이썬 리스트를 전부 훑어도 충분합니다.

마지막은 생성입니다. 찾은 조각을 프롬프트에 넣고, 문서에 없으면 없다고 답하라고 지시합니다.

```python
def ask(question, hits):
    context = "\n\n".join(f"[{c['title']}] {c['text']}" for _, c in hits)
    prompt = (
        "아래 [문서]에 있는 내용만 근거로 질문에 한국어로 짧게 답하세요.\n"
        "문서에 답이 없으면 '문서에 없는 내용입니다.'라고만 답하세요.\n\n"
        f"[문서]\n{context}\n\n[질문]\n{question}"
    )
    res = ollama.chat(
        model=CHAT_MODEL,
        messages=[{"role": "user", "content": prompt}],
        options={"temperature": 0, "seed": 42},
    )
    return res["message"]["content"].strip()


chunks = load_chunks(Path("docs/saju-terms.md"))
vectors = embed([f"{c['title']}\n{c['text']}" for c in chunks], "search_document: ")

question = "설을 쇠었지만 입춘 전에 태어났다면 연주는 어떻게 정하나요?"
hits = search(question, chunks, vectors)
for score, c in hits:
    print(f"검색 {score:.3f}  {c['title']}")
print(ask(question, hits))
```

실행 결과입니다.

```text
검색 0.804  연주와 입춘
검색 0.793  오행의 상승(상극)
검색 0.791  읽을 때 주의할 점
입춘 전에 태어났으면 지난해의 간지로 연주를 삼는다.
```

문서 내용 그대로 답했습니다. 13조각 임베딩은 모델이 메모리에 올라온 뒤 0.13초, 답변 생성은 0.2초 걸렸습니다. 같은 질문을 문서 없이 `gemma3:1b`에게 그냥 물으면, '연주'를 악기 연주로 받아들여 "전통적인 관점과 현대적인 관점을 조화롭게 융합해 연주하라"는 긴 글을 썼습니다.

## 5. 질문 8개로 시험해 보니: 검색이 절반은 빗나갔다

한 문제만 보고 안심하면 안 됩니다. 질문 8개를 만들어 돌렸습니다. 6개는 문서에 답이 있고, 2개는 일부러 문서에 없는 내용을 물었습니다.

| 질문 | 검색 1~3위에 정답 조각 | 문서를 넣은 답 |
|---|---|---|
| 천간은 모두 몇 가지이고 무엇인가요? | 있음(1위) | "10가지입니다." (이름은 빠뜨림) |
| 오행의 상생 순서를 알려 주세요. | **없음** | "문서에 없는 내용입니다." |
| 왜 사주를 팔자라고도 부르나요? | **없음** | 네 기둥 비유로 답함(틀림) |
| 설을 쇠었지만 입춘 전에 태어났다면 연주는? | 있음(1위) | 정답 |
| 가을은 오행 중 무엇에 해당하나요? | 있음(2위) | "금" (정답) |
| 사주를 보고 이직을 결정해도 될까요? | **없음** | "문서에 없는 내용입니다." |
| 2001년 3월 5일 오전 9시생의 사주 여덟 글자는? (가상의 날짜) | 문서에 없는 질문 | "문서에 없는 내용입니다." (바람직) |
| 천간의 갑은 오행 중 무엇에 속하나요? | 문서에 없는 질문 | "천간의 갑은 갑의 10가지에 속합니다." (틀림) |

답이 문서에 있는 6문항 중 3문항에서 정답 조각이 3위 안에 들지 못했습니다. "오행의 상생 순서"를 물었는데 '오행의 상생' 조각은 4위였고, 1위는 '오행의 상승(상극)'이었습니다. 점수를 보면 이유가 짐작됩니다. 13조각의 유사도가 대부분 0.75~0.80 사이에 몰려 있어 조각들을 잘 구분하지 못했습니다.

원인을 단정할 수는 없지만 확인된 사실은 이렇습니다. Hugging Face의 `nomic-embed-text` 모델 카드에 표시된 언어는 English뿐이고, 한국어 지원에 대한 설명은 없습니다. 한국어 문서를 다룬다면 **쓰려는 임베딩 모델이 한국어를 지원하는지 모델 카드에서 확인하고, 내 문서로 직접 시험해 보는 과정**이 꼭 필요합니다.

그래도 얻은 것이 있습니다. 검색이 빗나갔을 때 모델은 대체로 지어내지 않고 "문서에 없는 내용입니다."라고 답했습니다. 문서 없이 물었을 때 "천간은 음악의 음높이 간격"이라거나 "가을은 맥(木)"이라고 꾸며 낸 것과 비교하면, 틀린 답을 자신 있게 말하는 일은 줄었습니다.

## 6. 검색 고치기: 키워드 점수 더하기

검색을 고쳐 봅니다. 가장 단순한 방법은 **낱말이 겹치는 정도**를 점수에 더하는 것입니다. 한국어는 조사 때문에 띄어쓰기 단위로는 잘 맞지 않으므로, 글을 두 글자씩 잘라 겹치는 비율을 셉니다. '상생 순서'라면 '상생', '생순', '순서'가 됩니다.

```python
def bigrams(text):
    text = "".join(ch for ch in text if ch.isalnum())
    return {text[i:i + 2] for i in range(len(text) - 1)}


def keyword_score(question, doc):
    """질문의 두 글자 묶음 중 문서에도 나오는 비율."""
    q = bigrams(question)
    return len(q & bigrams(doc)) / len(q)


def search(question, chunks, vectors, hybrid=False):
    q = embed([question], "search_query: ")[0]
    scored = []
    for v, c in zip(vectors, chunks):
        score = cosine(q, v)
        if hybrid:  # 임베딩 점수에 키워드 점수를 더한다
            score += keyword_score(question, f"{c['title']}\n{c['text']}")
        scored.append((score, c))
    scored.sort(key=lambda s: s[0], reverse=True)
    return scored[:TOP_K]
```

코드에서는 두 점수를 섞는다는 뜻으로 이 옵션에 `hybrid`라는 이름을 붙였습니다. 답이 있는 6문항에서 정답 조각이 몇 위로 나오는지 네 가지 방식으로 비교했습니다.

| 질문 | 임베딩(접두어 있음) | 임베딩(접두어 없음) | 키워드만 | 임베딩+키워드 |
|---|---|---|---|---|
| 천간은 모두 몇 가지… | 1위 | 6위 | 1위 | 1위 |
| 오행의 상생 순서… | 4위 | 4위 | 1위 | 1위 |
| 왜 사주를 팔자라고도… | 4위 | 5위 | 1위 | 1위 |
| 설을 쇠었지만 입춘 전… | 1위 | 1위 | 1위 | 1위 |
| 가을은 오행 중… | 2위 | 3위 | 3위 | 1위 |
| 사주를 보고 이직을… | 8위 | 4위 | 1위 | 1위 |

둘을 더한 방식에서 6문항 모두 정답 조각이 1위가 됐습니다. 다만 이 결과는 조각 13개, 질문 6개짜리 작은 시험이고, 질문에 문서의 낱말이 그대로 들어 있어 키워드 검색에 유리했습니다. "어느 방식이 더 낫다"가 아니라 **내 문서와 내 질문으로 순위를 직접 재 봐야 한다**는 뜻으로 읽어 주세요. 접두어를 뺐을 때는 6문항 중 3문항에서 순위가 떨어지고 1문항에서 올랐습니다. 이 시험만으로 단정하기는 어렵지만, 모델 카드가 필수라고 안내하는 만큼 접두어는 붙여서 쓰는 편이 안전합니다.

## 7. 검색이 맞아도 답이 틀릴 수 있다

키워드를 더한 검색으로 8문항을 다시 돌렸습니다(`python rag.py --hybrid`).

```text
■ 질문: 오행의 상생 순서를 알려 주세요.
  검색 1.075  오행의 상생
  검색 1.022  오행의 상승(상극)
  검색 0.798  오행
  목은 화를 낳고, 화는 토를 낳고, 토는 금을 낳고, 금은 수를 낳고, 수는 목을 낳습니다.

■ 질문: 가을은 오행 중 무엇에 해당하나요?
  검색 0.913  오행과 방위, 계절
  가을은 금에 해당합니다.

■ 질문: 천간의 갑은 오행 중 무엇에 속하나요?
  문서에 없는 내용입니다.
```

상생 순서는 이제 문서대로 답했고, 문서에 없는 두 질문은 모두 "문서에 없는 내용입니다."로 답했습니다. 하지만 정답 조각을 1위로 넘겼는데도 답이 틀리거나 모자란 것이 셋 있었습니다.

- **옆 조각의 내용으로 답함:** "왜 팔자라고도 부르나요?"에 '팔자' 조각이 1위였지만, 3위로 함께 들어간 '사주' 조각의 네 기둥 비유를 이유로 답했습니다. 여덟 글자라서라는 답이 나와야 합니다.
- **문서에 있는데 없다고 함:** "이직을 결정해도 될까요?"에 '읽을 때 주의할 점' 조각이 1위였지만 "문서에 없는 내용입니다."라고 답했습니다. 문서에는 '취업'이라고 적혀 있고 '이직'이라는 낱말은 없습니다.
- **질문의 일부만 답함:** "몇 가지이고 무엇인가요?"에는 "10가지입니다."만 답하고 이름 10개는 말하지 않았습니다.

RAG는 **검색**과 **생성** 두 군데에서 틀릴 수 있습니다. 답이 이상하면 먼저 검색 결과를 출력해 어느 쪽 문제인지 나눠 봐야 합니다. 위 코드가 검색 점수와 조각 제목을 항상 찍는 이유입니다.

## 8. 한계와 주의할 점

- **결과 검증:** 문서를 넣어도 모델은 틀립니다. 질문과 기대 답을 미리 적어 두고, 코드나 문서를 바꿀 때마다 다시 돌려 확인하세요. 평균 점수만 보면 놓치는 것이 있다는 이야기는 [LLM 평가 글](/2026/11/24/llm-eval-average-score-trap/)에 정리했습니다.
- **인덱싱과 질문에 같은 모델:** Ollama 문서는 문서를 임베딩할 때와 질문을 임베딩할 때 같은 모델을 쓰라고 안내합니다. 임베딩 모델을 바꾸면 문서 벡터도 전부 다시 만들어야 합니다.
- **긴 문서:** `/api/embed`는 기본값(`truncate: true`)에서 컨텍스트를 넘는 입력을 잘라 냅니다. Ollama 라이브러리 페이지는 `nomic-embed-text`의 컨텍스트를 2K로 표시합니다. 조각은 짧게 나누세요.
- **문서의 정확성:** RAG는 문서가 틀리면 틀린 답을 합니다. 이 예제의 용어 설명은 백과사전에서 확인한 범위로만 썼고, 확인하지 못한 내용(천간별 오행 배속 등)은 넣지 않았습니다.
- **사주의 쓰임:** 이 예제는 용어 사전입니다. 실제 생년월일의 사주를 계산하거나 운세를 풀이하지 못하며, 그렇게 쓰이도록 만들지도 않았습니다. 사주풀이는 과학적 근거가 없으므로 중요한 결정의 근거로 삼지 마세요.
- **라이선스:** `nomic-embed-text`는 Apache License 2.0, `gemma3`는 Gemma Terms of Use를 따릅니다. 업무나 서비스에 쓰기 전에 `ollama show`로 확인하세요. 내 문서로 쓰려는 자료의 저작권도 따로 확인해야 합니다.
- **개인정보·사내 규정:** 모델이 내 컴퓨터에서 돌아 문서가 밖으로 나가지 않는다는 점은 로컬 RAG의 장점입니다. 그래도 회사 문서나 다른 사람의 개인정보(생년월일 포함)를 넣기 전에는 사내 규정을 확인하세요.

## 마무리

- RAG는 문서 조각을 임베딩해 두고, 질문과 비슷한 조각을 찾아 프롬프트에 넣어 답하게 하는 방식입니다.
- Ollama의 `/api/embed`와 파이썬 리스트, 코사인 유사도만으로 가장 간단한 RAG를 만들 수 있습니다.
- `nomic-embed-text`는 문서에 `search_document: `, 질문에 `search_query: ` 접두어를 붙여야 합니다.
- 이 실험에서 임베딩만으로는 한국어 검색이 6문항 중 3문항에서 빗나갔고, 키워드 점수를 더하자 모두 1위로 올라왔습니다. 내 문서로 직접 재 보는 것이 중요합니다.
- 검색이 맞아도 작은 모델은 답을 틀릴 수 있습니다. 검색 결과와 답을 따로 확인하세요.
