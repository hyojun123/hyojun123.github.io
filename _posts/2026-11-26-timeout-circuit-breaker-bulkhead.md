## 죽은 서비스보다 느린 서비스가 더 위험하다

의존하는 서비스가 완전히 죽으면 연결이 바로 거절되니 호출한 쪽도 금방 오류를 받습니다. 정말 곤란한 건 **죽지는 않았는데 응답이 오지 않는** 경우입니다. 호출한 쪽은 응답을 기다리며 스레드, 연결, 메모리를 붙잡고 있고, 그 자원이 바닥나면 그 서비스와 아무 상관 없는 기능까지 함께 멈춥니다.

추천 서비스 하나가 느려졌을 뿐인데 상품 목록, 로그인, 결제까지 응답하지 않는 장애가 이렇게 만들어집니다. 이 글은 Node.js로 만든 작은 게이트웨이에서 이 전파 과정을 재현하고, 타임아웃·벌크헤드·서킷 브레이커를 하나씩, 그리고 함께 적용했을 때 무엇이 달라지는지 측정한 결과를 정리합니다.

<!--more-->

글의 숫자는 노트북의 Node.js v24에서 **한 프로세스 안에 띄운 HTTP 서버 세 개**(게이트웨이 1개, 가짜 백엔드 2개)로 측정한 예제 결과입니다. Docker나 외부 패키지는 쓰지 않았고, 백엔드의 지연은 타이머로 흉내 냈습니다. 실제 서비스의 수치가 아니며 환경과 설정에 따라 달라집니다.

## 1. 장애는 왜 옆으로 번지나

핵심은 **공유 자원**입니다. 서버는 요청을 처리할 때 스레드, 커넥션 풀의 연결, 메모리 같은 한정된 자원을 씁니다. 평소에는 요청이 금방 끝나 자원이 바로 돌아오지만, 의존 서비스가 응답하지 않으면 그 호출이 자원을 쥔 채로 멈춰 있습니다.

Google SRE 책의 연쇄 장애 장은 이를 숫자로 보여 줍니다. 작업 스레드가 100개인 프런트엔드 10대(합계 1,000개)가 초당 1,000건을 100ms에 처리하면 평소에는 스레드 100개 정도만 바쁩니다. 그런데 요청의 5%가 끝나지 않고 데드라인까지 버티게 되면, 데드라인이 100초일 때 그 5%가 스레드 5,000개를 필요로 합니다. 가진 스레드는 1,000개뿐이라 책의 계산으로는 요청의 약 19.6%만 처리되고 80.4%가 오류가 됩니다. **5%만 실패했어야 할 장애가 대부분의 요청을 실패하게 만든 것**입니다.

AWS Builders' Library의 글도 같은 점을 짚습니다. 클라이언트가 평소보다 오래 기다리면 그동안 쓰던 자원을 계속 붙잡고, 이런 요청이 많아지면 서버의 메모리, 스레드, 연결, 임시 포트 같은 한정된 자원이 바닥날 수 있다는 것입니다.

막는 방법은 세 가지 질문으로 나눌 수 있습니다.

| 질문 | 장치 | 하는 일 |
|---|---|---|
| 얼마나 오래 기다릴 것인가 | 타임아웃 | 호출 하나가 자원을 쥐는 시간에 상한을 둔다 |
| 한 의존 서비스에 자원을 얼마나 내줄 것인가 | 벌크헤드 | 의존 서비스별로 쓸 수 있는 자원을 나눠 둔다 |
| 실패할 게 뻔한 호출을 계속 보낼 것인가 | 서킷 브레이커 | 실패가 쌓이면 호출 자체를 건너뛴다 |

## 2. 실험 구성

게이트웨이는 두 API를 제공하고, 각각 다른 백엔드를 호출합니다.

| 구성 요소 | 설정 |
|---|---|
| `/products` → catalog | 항상 정상. 응답 20~30ms |
| `/recommend` → reco | 평소 20~30ms. **4~12초 구간(8초)에는 응답에 10초가 걸림** |
| 게이트웨이 | 동시에 20건까지만 처리(작업 슬롯 20개). 넘치면 줄을 섬 |
| 부하 | 20초 동안 초당 약 90건, 두 API를 번갈아 호출 |
| 사용자 | 2초 안에 응답이 없으면 포기 |

Node.js는 요청마다 스레드를 쓰지 않으므로, 스레드 풀이나 DB 커넥션 풀처럼 **개수가 정해진 공유 자원**을 세마포어 하나(작업 슬롯 20개)로 흉내 냈습니다. 평소에는 요청이 약 26ms 만에 끝나서 슬롯은 2~3개만 쓰입니다.

게이트웨이가 백엔드를 부르는 코드는 다음과 같습니다. `timeoutMs`가 없으면 응답이 올 때까지 기다립니다.

```js
function callDep(port, { agent, timeoutMs }) {
  return new Promise((resolve, reject) => {
    const options = { host: '127.0.0.1', port, path: '/', agent };
    if (timeoutMs) options.signal = AbortSignal.timeout(timeoutMs);
    const req = http.get(options, (res) => {
      res.resume();
      res.on('end', resolve);
      res.on('error', reject);
    });
    req.on('error', reject);
  });
}
```

## 3. 재현: 추천이 느려지자 상품 목록이 죽었다

먼저 아무 대비 없이 돌렸습니다. 아래는 reco가 느려진 8초 동안 들어온 요청의 결과이고, 세 번 반복한 범위입니다.

| API | 요청 수 | 2초 안에 성공 | 사용자가 포기 |
|---|---|---|---|
| `/products` (정상 백엔드) | 354~357 | 19~20 | 335~338 |
| `/recommend` (느린 백엔드) | 355~358 | 0 | 355~358 |

catalog 백엔드는 실험 내내 멀쩡했는데도 `/products` 요청의 약 94%가 실패했습니다. 장애가 시작되고 0.5초도 지나지 않아 reco 호출 20개가 작업 슬롯 20개를 모두 차지했고, 그 뒤에 들어온 요청은 종류와 상관없이 줄만 섰기 때문입니다. 줄은 최대 852~858건까지 길어졌습니다.

복구도 느렸습니다. reco는 12초에 정상으로 돌아왔지만, 슬롯을 쥔 호출들은 10초를 다 채운 14초 무렵에야 끝났습니다. 그다음에는 **사용자가 이미 떠난 요청 약 800건**을 게이트웨이가 차례로 처리했고, 그동안 새로 들어온 요청은 또 기다렸습니다. 결국 장애 원인이 사라진 뒤에도 약 1.2초 동안 들어온 요청(양쪽 API 각각 54~56건)이 추가로 실패했습니다.

## 4. 방법 1: 타임아웃, 다만 값이 중요하다

가장 먼저 할 일은 모든 원격 호출에 타임아웃을 거는 것입니다. AWS 글은 원격 호출은 물론이고 같은 장비 안의 프로세스 간 호출에도 타임아웃을 두라고 권합니다. Node.js에서는 `http.request`의 `signal` 옵션에 `AbortSignal.timeout(ms)`를 넘기면 됩니다. 공식 문서는 이 함수를 지정한 밀리초 뒤에 중단되는 `AbortSignal`을 돌려준다고 설명합니다.

타임아웃을 1,000ms와 300ms 두 가지로 걸어 같은 실험을 반복했습니다.

| 설정 | `/products` 성공 (장애 구간) | `/products` p99 | 슬롯 대기 줄 최대 | reco로 간 호출 |
|---|---|---|---|---|
| 타임아웃 없음 | 19~20 / 354~357 | 2,004ms (포기) | 852~858 | 20 |
| 타임아웃 1,000ms | 133~135 / 363~364 | 2,003~2,005ms (포기) | 422~427 | 160 |
| 타임아웃 300ms | 367~368 / 367~368 | 32~34ms | 0 | 367~368 |

타임아웃 1,000ms는 **걸려 있는데도 `/products`의 63%가 실패**했습니다. 계산해 보면 당연합니다. `/recommend`가 초당 약 45건 들어오고 호출 하나가 슬롯을 1초씩 쥐므로 슬롯이 45개쯤 필요한데, 가진 것은 20개입니다. 300ms로 줄이면 필요한 슬롯이 45 × 0.3 ≈ 14개로 줄어 20개 안에 들어오고, `/products`는 전혀 영향을 받지 않았습니다.

즉 타임아웃은 "있다/없다"가 아니라 **(초당 호출 수) × (타임아웃)이 공유 자원 크기보다 작은가**가 관건입니다. SRE 책도 평균 지연보다 몇 자릿수 큰 데드라인은 대체로 좋지 않다고 말합니다. 이 실험에서 평소 응답은 약 26ms였으니 1,000ms는 약 40배, 300ms는 약 12배입니다.

### 그럼 값은 어떻게 정하나

AWS 글이 소개하는 방법은 이렇습니다. 먼저 정상인데도 타임아웃으로 끊겨도 괜찮은 비율(예: 0.1%)을 정하고, 호출 대상 서비스의 지연 지표에서 그에 해당하는 백분위(예: p99.9)를 타임아웃으로 잡습니다. 같은 글은 이 방법이 잘 맞지 않는 경우도 함께 적어 두었습니다.

- 인터넷을 거치는 클라이언트처럼 네트워크 지연이 큰 경우에는 최악의 네트워크 지연을 감안해야 합니다.
- p99.9와 p50이 가까운 서비스는 여유를 조금 더해야 작은 지연 증가에 타임아웃이 쏟아지지 않습니다.
- 타임아웃이 DNS 조회나 TLS 핸드셰이크까지 덮는지 확인해야 합니다.

마지막 항목과 관련해 같은 글은 약 20ms로 잡은 타임아웃이 배포 직후에만 터졌던 사례를 듭니다. 새 연결을 맺는 시간이 타임아웃에 포함돼 있었기 때문이고, 프로세스 시작 시 연결을 미리 맺어 두는 방식으로 개선했다고 합니다.

반대로 너무 짧게 잡으면 정상 요청까지 끊기고, 끊긴 요청이 재시도되면서 부하가 늘어납니다. 재시도가 부하를 키우는 과정은 [재시도 폭풍 글](/2026/11/25/retry-backoff-jitter-budget/)에서 다뤘습니다.

### 기본값을 믿으면 안 되는 이유

타임아웃을 직접 지정하지 않으면 라이브러리 기본값이 쓰이는데, 대개 사람이 기다릴 수 있는 시간보다 훨씬 깁니다. Node.js 내장 `fetch`가 기반으로 삼는 undici의 Client 문서를 보면 `headersTimeout`과 `bodyTimeout`의 기본값이 각각 300초, `connectTimeout`이 10초입니다. `http.request`의 `timeout` 옵션도 주의가 필요합니다. 공식 문서는 `'timeout'` 이벤트가 소켓이 한동안 조용했다는 사실만 알릴 뿐이며 요청은 직접 `destroy`해야 한다고 설명합니다.

## 5. 방법 2: 벌크헤드, 칸을 나눠 한 곳만 잠기게

타임아웃 값을 완벽하게 맞추기는 어렵습니다. 트래픽이 늘면 같은 타임아웃으로도 슬롯이 모자랄 수 있습니다. 벌크헤드(bulkhead)는 **의존 서비스 하나가 쓸 수 있는 자원에 상한**을 두어, 최악의 경우에도 나머지 자원이 남게 합니다.

Azure Architecture Center의 벌크헤드 패턴 문서는 이름이 배의 선체를 나눈 격벽에서 왔다고 설명합니다. 선체가 뚫려도 그 칸에만 물이 차서 배 전체가 가라앉지 않는 것처럼, 여러 서비스를 호출하는 쪽이 서비스별로 연결 풀을 따로 두면 한 서비스가 응답하지 않아도 그 풀만 영향을 받는다는 것입니다.

예제에서는 reco 호출이 동시에 10개를 넘으면 **기다리지 않고 바로 거절**하는 세마포어를 썼습니다.

```js
const recoBulkhead = new Semaphore(10);        // reco에는 슬롯을 10개까지만 내준다

async function callReco() {
  if (!recoBulkhead.tryAcquire()) {            // 칸이 꽉 찼으면 줄 서지 않고 실패
    throw new Error('bulkhead full');
  }
  try {
    await callDep(RECO, { agent, timeoutMs });
  } finally {
    recoBulkhead.release();
  }
}
```

| 설정 | `/products` 성공 (장애 구간) | `/products` p99 | `/recommend` 응답 시간 p50 / p99 | reco로 간 호출 |
|---|---|---|---|---|
| 벌크헤드만 (타임아웃 없음) | 359 / 359 | 32~33ms | 0ms / 2,001ms | 10 |
| 타임아웃 1,000ms + 벌크헤드 | 전부 성공 | 33~34ms | 1ms / 1,003ms | 80 |

앞에서 실패했던 타임아웃 1,000ms 설정도 벌크헤드를 더하자 `/products`가 전부 성공했습니다. reco가 아무리 느려도 슬롯 20개 중 10개는 남기 때문입니다. `/recommend`는 대부분 1ms 안에 오류(504)를 받았습니다. 느린 실패가 빠른 실패로 바뀐 것입니다.

다만 벌크헤드만 쓰고 타임아웃이 없으면 문제가 남습니다. 처음 들어간 10건이 10초 동안 칸을 채우고 있어서, reco가 복구된 뒤에도 약 2초 동안 `/recommend` 91~92건이 더 거절됐습니다. **벌크헤드는 피해 범위를 가두고, 타임아웃은 칸을 비워 줍니다.** 둘은 서로를 대신하지 못합니다.

## 6. 방법 3: 서킷 브레이커, 안 될 호출은 보내지 않는다

타임아웃과 벌크헤드를 써도 장애 구간 내내 reco로 호출이 계속 나갑니다. 호출마다 타임아웃만큼 기다렸다가 실패하고, 이미 힘든 reco에는 부하가 더해집니다. 서킷 브레이커는 실패가 쌓이면 **호출을 아예 건너뛰고 바로 실패**하게 합니다.

Azure의 서킷 브레이커 패턴 문서는 이를 세 가지 상태를 가진 상태 기계로 설명합니다.

| 상태 | 동작 |
|---|---|
| Closed (닫힘) | 호출을 그대로 보낸다. 최근 실패 수를 세고, 정해진 시간 안에 임계값을 넘으면 Open으로 간다 |
| Open (열림) | 호출하지 않고 즉시 실패한다. 타이머가 끝나면 Half-Open으로 간다 |
| Half-Open (반열림) | 제한된 수의 요청만 통과시킨다. 정해진 횟수만큼 연속 성공하면 Closed로, 하나라도 실패하면 다시 Open으로 간다 |

문서는 Half-Open을 두는 이유를 복구 중인 서비스에 요청이 한꺼번에 쏟아지지 않게 하기 위해서라고 설명합니다. 예제의 브레이커는 10초 안에 5번 실패하면 열리고, 1초 뒤 시험 요청을 한 번에 하나씩 보내며, 2번 연속 성공하면 닫힙니다.

```js
async exec(fn) {
  if (this.state === 'open') {
    if (Date.now() - this.openedAt < this.openMs) throw new Error('circuit open');
    this._to('half-open');
    this.successes = 0;
  }
  if (this.state === 'half-open') {
    if (this.trialInFlight) throw new Error('circuit open');  // 시험 요청은 한 번에 하나
    this.trialInFlight = true;
    try {
      const v = await fn();
      if (++this.successes >= this.successThreshold) { this.failures = []; this._to('closed'); }
      return v;
    } catch (e) {
      this.openedAt = Date.now();
      this._to('open');
      throw e;
    } finally {
      this.trialInFlight = false;
    }
  }
  try {
    return await fn();
  } catch (e) {                                  // Closed: 최근 실패를 세다가 임계값을 넘으면 연다
    const now = Date.now();
    this.failures = this.failures.filter((t) => now - t < this.windowMs);
    this.failures.push(now);
    if (this.state === 'closed' && this.failures.length >= this.failureThreshold) {
      this.openedAt = now;
      this._to('open');
    }
    throw e;
  }
}
```

브레이커가 열려 있거나 호출이 실패하면 게이트웨이는 오류 대신 **추천 없는 기본 응답**(예제에서는 `degraded`)을 200으로 돌려주게 했습니다. Azure 문서도 Open 상태에서 예외 대신 기본값을 돌려주는 변형을 언급합니다.

| 설정 | `/products` p99 (장애 구간) | `/recommend` 결과 | `/recommend` p50 / p99 | reco로 간 호출 |
|---|---|---|---|---|
| 타임아웃 1,000ms + 브레이커 | 600~611ms | 전부 기본 응답 | 1ms / 1,019~1,024ms | 26 |
| 타임아웃 300ms + 벌크헤드 + 브레이커 | 33ms | 전부 기본 응답 | 0~1ms / 302~303ms | 16 |

장애 8초 동안 reco로 간 호출은 타임아웃만 쓸 때의 160건(1,000ms)·367~368건(300ms)에서 26건·16건으로 줄었습니다. `/recommend` 사용자는 오류 화면 대신 대부분 1ms 만에 기본 응답을 받았습니다.

### 브레이커만으로는 처음 1초가 비어 있다

첫 번째 줄의 `/products` p99가 600ms대인 점을 봐야 합니다. 요청이 실패하지는 않았지만 평소 p99(33ms 안팎)의 약 18배로 느려졌습니다. 브레이커는 **실패를 5번 확인한 뒤에야** 열리는데, 타임아웃이 1,000ms라 첫 실패가 장애 시작 1초 뒤에야 나옵니다(브레이커는 세 번 모두 5.09초에 열렸습니다). 그 1초 동안 reco 호출이 슬롯을 다 차지해 줄이 53~55건까지 생겼습니다.

벌크헤드와 짧은 타임아웃을 함께 쓴 두 번째 줄에서는 브레이커가 4.31~4.32초에 열렸고 줄이 한 번도 생기지 않았습니다. 브레이커가 열리기 전의 공백을 벌크헤드가 메운 셈입니다.

### 복구를 알아차리는 데도 시간이 든다

브레이커를 쓰면 복구가 조금 늦어집니다. 세 가지를 모두 쓴 설정에서 reco는 12초에 복구됐지만 브레이커는 13.26~13.29초에 닫혔고, 그 사이 `/recommend` 56~57건이 기본 응답을 받았습니다. 11.9초 무렵에 보낸 시험 요청이 장애 구간에 걸려 실패하면서 1초를 더 기다렸기 때문입니다.

타임아웃 1,000ms 설정에서는 시험 요청 시점이 우연히 복구 직후(12.14초)에 맞아 12.19~12.21초에 닫혔고 7~8건만 기본 응답을 받았습니다. 어느 쪽이든 **Open 유지 시간만큼은 복구 감지가 늦어질 수 있다**는 점을 감안해야 합니다. Azure 문서도 Open에 너무 오래 머무는 것과 너무 빨리 Half-Open으로 가는 것 모두 문제가 될 수 있다고 적고 있습니다.

## 7. 기대와 달랐던 결과: 연결 풀을 같이 써도 번지지 않은 경우

처음에는 작업 슬롯 대신 Node.js `http.Agent`의 연결 풀 하나(`keepAlive: true`, `maxTotalSockets: 20`)를 두 백엔드가 같이 쓰게 해서 재현하려 했습니다. reco 호출이 소켓 20개를 다 차지하면 catalog 호출도 막힐 것이라 예상했습니다.

결과는 달랐습니다. 타임아웃이 없는데도 `/products`는 장애 구간 358~361건이 전부 성공했습니다. 풀을 들여다보니 reco가 차지한 소켓은 최대 18개였고, 나머지 2개는 catalog와 맺어 둔 keep-alive 연결이었습니다. catalog 요청이 이 2개를 계속 재사용한 덕에 reco 쪽 요청 430여 건이 풀에서 대기하는 동안에도 catalog는 막히지 않았습니다.

이 결과를 "연결 풀을 같이 써도 안전하다"로 읽으면 안 됩니다. 이 실험의 트래픽 패턴과 Agent 설정에서 그랬을 뿐이고, 연결을 재사용하지 않거나 catalog 연결이 유휴 시간 초과로 닫히면 결과가 달라질 수 있습니다. 여기서 얻을 교훈은 **장애가 번지는지는 자원이 실제로 어떻게 공유되는지에 달려 있고, 직접 재현해 보기 전에는 단정하기 어렵다**는 점입니다.

## 8. 주의할 점과 한계

- **타임아웃이 덮지 않는 대기 시간:** 예제의 타임아웃은 작업 슬롯을 얻은 뒤부터 잽니다. 그래서 타임아웃 1,000ms 설정에서도 요청이 슬롯을 기다리며 2초 넘게 줄에 서 있었습니다. SRE 책은 서버가 각 단계에서 남은 데드라인을 확인하고, 이미 지났다면 일을 하지 말라고 권합니다.
- **데드라인 전파:** 같은 책은 데드라인을 호출 경로를 따라 전달하라고 설명합니다. A가 30초 데드라인으로 시작해 7초를 쓰고 B를 부르면 B에게는 23초가, B가 4초를 쓰고 C를 부르면 C에게는 19초가 주어지는 식입니다. 이 예제는 전파를 구현하지 않아서, 사용자가 떠난 요청을 게이트웨이가 끝까지 처리했습니다.
- **대기 줄 길이:** 예제의 슬롯 대기 줄은 길이 제한이 없어 850건까지 쌓였습니다. SRE 책은 트래픽이 일정한 서비스라면 대기 줄을 스레드 풀 크기의 50% 이하로 작게 두어, 감당하지 못할 때 일찍 거절하라고 권합니다.
- **브레이커는 의존 대상별로:** Azure 문서는 서로 독립적인 여러 제공자(예: 데이터 저장소의 샤드)를 브레이커 하나로 묶으면 멀쩡한 쪽까지 막거나 고장 난 쪽으로 호출이 나갈 수 있다고 경고합니다.
- **재시도와 함께 쓸 때:** 같은 문서는 재시도를 브레이커를 거쳐서 하되, 브레이커가 일시적 장애가 아니라고 알리면 재시도를 멈추라고 설명합니다.
- **비용:** 벌크헤드는 자원을 나눠 묶어 두는 만큼 평소 효율이 떨어집니다. Azure 문서도 자원 효율 저하를 받아들일 수 없거나 복잡도를 감당할 필요가 없는 경우에는 맞지 않을 수 있다고 적습니다.
- **예제의 단순함:** 인스턴스 1대, 백엔드 2개, 고정된 부하로 측정했습니다. 임계값(5회, 1초, 10개)은 설명을 위한 값이지 권장값이 아닙니다.

## 9. 어떤 방법을 고를까

| 상황 | 먼저 할 일 |
|---|---|
| 원격 호출에 타임아웃이 없거나 기본값 그대로 | 모든 호출에 타임아웃을 명시한다. 값은 대상 서비스의 지연 백분위에서 시작한다 |
| 타임아웃은 있는데 한 서비스 장애에 다른 기능이 느려짐 | (초당 호출 수 × 타임아웃)을 공유 자원 크기와 비교하고, 의존 서비스별 동시 호출 상한(벌크헤드)을 둔다 |
| 장애 중에도 죽은 서비스로 호출이 계속 나감 | 서킷 브레이커로 호출을 건너뛰고, 가능하면 기본 응답을 준비한다 |
| 없어도 화면을 보여 줄 수 있는 부가 기능(추천, 배너 등) | 짧은 타임아웃 + 브레이커 + 기본 응답 |
| 반드시 성공해야 하는 핵심 호출(결제 등) | 타임아웃과 벌크헤드로 격리하되, 기본 응답 대신 명확한 오류를 돌려준다 |
| 호출 경로가 여러 단계 | 데드라인을 전파하고 단계마다 남은 시간을 확인한다 |

순서를 정한다면 **타임아웃 → 벌크헤드 → 서킷 브레이커**입니다. 타임아웃이 없으면 나머지 둘도 제대로 동작하지 않습니다. 벌크헤드는 칸이 비지 않고, 브레이커는 실패를 세지 못합니다.

## 마무리

- 응답하지 않는 의존 서비스는 호출한 쪽의 공유 자원을 붙잡아, 상관없는 기능까지 멈추게 합니다. 예제에서는 정상 API의 요청 약 94%가 실패했습니다.
- 타임아웃은 **있는 것만으로는 부족**합니다. (초당 호출 수) × (타임아웃)이 공유 자원보다 크면 여전히 번집니다.
- 벌크헤드는 의존 서비스별 자원 상한으로 **피해 범위를 가두고**, 느린 실패를 빠른 실패로 바꿉니다.
- 서킷 브레이커는 **안 될 호출을 보내지 않아** 장애 중인 서비스의 부하와 사용자의 대기 시간을 줄입니다. 대신 열리기 전과 닫히기 전에 공백이 있습니다.
- 세 장치는 서로의 빈틈을 메웁니다. 예제에서 셋을 함께 썼을 때만 정상 API가 평소 속도를 유지하면서 느린 서비스로 가는 호출이 16건까지 줄었습니다.

예제는 Node.js 표준 라이브러리만으로 만들었습니다. 위 코드 조각에 가짜 백엔드, 세마포어, 측정 코드를 더하면 같은 실험을 해 볼 수 있습니다. 캐시 만료로 DB에 요청이 몰리는 다른 종류의 과부하는 [캐시 스탬피드 글](/2026/11/24/cache-stampede-redis/)에서 다뤘습니다.
