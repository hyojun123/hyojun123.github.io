## 좋은 뜻으로 넣은 재시도가 장애를 키운다

다른 서비스를 호출하다 실패하면 한 번 더 시도하는 코드는 어디에나 있습니다. 네트워크가 잠깐 끊기거나 서버 한 대가 재시작하는 정도의 일시적인 실패라면, 재시도는 사용자가 오류를 보지 않게 해 주는 좋은 장치입니다.

문제는 실패의 원인이 **과부하**일 때입니다. 이미 힘든 서버에 실패한 요청이 다시 돌아오면 부하는 더 커지고, 더 많은 요청이 실패하고, 그 요청들이 또 재시도합니다. 이런 현상을 흔히 재시도 폭풍(retry storm)이라고 부릅니다. 이 글은 Node.js로 만든 가짜 서버에서 재시도 폭풍을 재현하고, 지수 백오프·지터·재시도 예산을 차례로 적용해 무엇이 어디까지 막아 주는지 측정한 결과를 정리합니다.

<!--more-->

글의 숫자는 노트북의 Node.js v24에서 **한 프로세스 안에 만든 가짜 서버**(동시에 10개 처리, 요청 하나에 25ms, 대기 줄 200개, 즉 초당 약 400건 처리)로 측정한 예제 결과입니다. 네트워크도 Docker도 쓰지 않았고, 타이머만으로 지연을 흉내 냈습니다. 실제 서비스의 수치가 아니며 환경과 설정에 따라 달라집니다.

## 1. 재시도는 왜 장애를 키우나

AWS Builders' Library의 글은 재시도를 "이기적"이라고 표현합니다. 클라이언트가 자기 요청의 성공 확률을 높이려고 서버의 시간을 더 쓰는 행동이기 때문입니다. 실패가 드물 때는 문제가 없지만, 실패 원인이 과부하라면 재시도가 상황을 훨씬 나쁘게 만들고, **원래 문제가 해결된 뒤에도 부하를 높게 유지해 회복을 늦출 수 있다**고 설명합니다.

Google SRE 책은 숫자로 예를 듭니다. 초당 10,000건까지 처리하는 백엔드에 10,100건이 들어오면 100건이 거절됩니다. 이 100건이 재시도로 돌아오면 다음에는 10,200건이 들어오고, 실패가 200건으로 늘어납니다. 재시도가 쌓일수록 첫 시도에 성공하는 요청은 줄어듭니다.

계층이 여러 개면 곱셈이 됩니다. 같은 책은 프런트엔드 자바스크립트, 프런트엔드 서버, 백엔드가 각각 3번씩 재시도(4번 시도)하면 사용자 동작 한 번이 DB에 64번(4의 3제곱)의 시도를 만들 수 있다고 설명합니다. AWS 글도 5개 계층이 각각 3번씩 시도하면 DB 부하가 243배가 되는 예를 듭니다.

정리하면 재시도에는 서로 다른 문제가 세 가지 있습니다.

| 문제 | 설명 | 주로 막는 방법 |
|---|---|---|
| 동시에 몰림 | 같은 순간 실패한 요청들이 같은 순간 다시 온다 | 백오프 + 지터 |
| 총량 증가 | 실패가 많을수록 전체 요청 수가 몇 배로 는다 | 시도 횟수 제한, 재시도 예산 |
| 계층 곱셈 | 여러 계층이 각자 재시도해 곱으로 는다 | 한 계층에서만 재시도 |

이 구분이 중요한 이유는, 뒤의 실험에서 보겠지만 **첫 번째를 막는 방법이 두 번째를 막아 주지는 않기** 때문입니다.

## 2. 실험에 쓴 재시도 코드

모든 실험은 아래 함수 하나로 호출합니다. 시도마다 타임아웃을 걸고, 실패하면 정책이 정한 시간만큼 기다렸다가 다시 시도합니다. `budget`은 5장에서 설명합니다.

```js
async function callWithRetry(server, { timeoutMs, maxAttempts, backoff, budget }) {
  if (budget) budget.onFirstAttempt();
  for (let attempt = 0; attempt < maxAttempts; attempt++) {
    try {
      await attemptOnce(server, timeoutMs);     // 타임아웃이 있는 한 번의 시도
      return attempt + 1;
    } catch (e) {
      if (attempt === maxAttempts - 1) return 0;
      if (budget && !budget.tryRetry()) return 0;
      const wait = backoff(attempt);
      if (wait > 0) await sleep(wait);
    }
  }
  return 0;
}
```

가짜 서버는 대기 줄이 꽉 차면 요청을 바로 거절합니다(HTTP라면 503에 해당). 그리고 클라이언트가 타임아웃으로 떠나도 그 사실을 모른 채 **줄에 있던 요청을 끝까지 처리**합니다. 타임아웃을 서버로 전달하지 않는 평범한 구성을 흉내 낸 것입니다.

## 3. 실험 1: 동시에 실패한 1,000개가 다시 몰려온다

서버가 1초 동안 모든 요청을 거절하는 상황에서 클라이언트 1,000개가 동시에 요청을 보냈습니다. 배포 직후나 순간적인 네트워크 단절 뒤에 클라이언트가 한꺼번에 붙는 상황입니다. 시도는 최대 10번, 백오프의 기준 값(base)은 100ms, 상한(cap)은 2초로 두었습니다.

대기 시간을 정하는 방법은 AWS Architecture Blog의 글과 그 글이 공개한 시뮬레이터 코드를 따랐습니다.

```js
const expo = (base, cap, attempt) => Math.min(cap, base * 2 ** attempt);

const backoffs = {
  // 지수 백오프(지터 없음): 100, 200, 400, 800, ... 최대 cap
  expo: (base, cap) => (attempt) => expo(base, cap, attempt),
  // Full Jitter: 0과 지수 백오프 값 사이의 무작위 값
  fullJitter: (base, cap) => (attempt) => rand(0, expo(base, cap, attempt)),
  // Equal Jitter: 절반은 그대로 두고 나머지 절반만 무작위
  equalJitter: (base, cap) => (attempt) => {
    const v = expo(base, cap, attempt);
    return v / 2 + rand(0, v / 2);
  },
  // Decorrelated Jitter: 직전 대기 시간의 3배까지에서 무작위
  decorrelated: (base, cap) => {
    let prev = base;
    return () => (prev = Math.min(cap, rand(base, prev * 3)));
  },
};
```

세 번 반복한 결과입니다. "복구 뒤 최대 몰림"은 서버가 살아난 1초 이후, 100ms 구간 하나에 도착한 요청 수의 최댓값입니다.

| 정책 | 서버에 도착한 요청 | 복구 뒤 최대 몰림(100ms당) | 성공한 클라이언트 | 모두 끝난 시각 |
|---|---|---|---|---|
| 즉시 재시도 | 10,000 | - | 0 | 31~38ms |
| 고정 100ms 대기 | 10,000 | - | 0 | 약 950ms |
| 지수 백오프(지터 없음) | 6,900 | 1,000 | 1,000 | 약 9.6초 |
| Equal Jitter | 5,698~5,711 | 242~258 | 1,000 | 4.6~4.7초 |
| Full Jitter | 6,283~6,293 | 147~166 | 1,000 | 4.1~4.5초 |
| Decorrelated Jitter | 5,139~5,251 | 186~192 | 998~1,000 | 4.1~4.4초 |

### 즉시 재시도는 기회를 그냥 태운다

즉시 재시도는 10번의 시도를 0.04초 안에 모두 써 버렸습니다. 서버가 1초 뒤에 살아났지만 그때는 이미 모든 클라이언트가 포기한 뒤입니다. 고정 100ms 대기도 마지막 시도가 약 0.9초 시점이라 한 건도 성공하지 못했습니다. 이 수치는 "장애 1초, 시도 10번"이라는 조건이 만든 결과이지만, 간격이 늘지 않는 재시도는 **장애가 조금만 길어져도 쓸모가 없다**는 점을 보여 줍니다.

### 지수 백오프만으로는 몰림이 그대로다

지수 백오프는 대기 시간을 두 배씩 늘려 더 오래 버팁니다. 그래서 1,000개 모두 결국 성공했습니다. 하지만 100ms 구간별 도착 수를 찍어 보면 이렇게 나옵니다.

```text
지수 백오프(지터 없음) | 1000 1000 0 1000 0 0 0 1000 0 0 0 0 0 0 0 1000 0 0 ...
Full Jitter           | 2069  718 559 329 320 292 159 168 187 164 159 111 90 65 72 ...
```

지터가 없으면 1,000개가 **똑같은 시각에 깨어나 한꺼번에** 옵니다. 서버가 살아난 뒤에도 마찬가지여서, 1,000건이 도착하면 약 210건(처리 중 10 + 대기 줄 200)만 받아들여지고 나머지는 거절돼 다음 차례(2초 뒤)로 밀립니다. 그래서 모두 끝나는 데 약 9.6초가 걸렸습니다. AWS 글이 지적한 대로, 백오프만으로는 호출이 뭉치는 구간과 아무도 호출하지 않는 빈 구간이 생길 뿐입니다.

### 지터는 같은 일을 절반 시간에 끝낸다

지터를 넣으면 복구 뒤 최대 몰림이 1,000건에서 147~258건으로 줄었고, 전체가 끝나는 시간도 절반 이하가 됐습니다. 서버가 쉬는 구간 없이 꾸준히 일할 수 있었기 때문입니다.

세 가지 지터 사이의 차이는 이 실험에서는 크지 않았고, 순서도 AWS 글의 시뮬레이션과 완전히 같지는 않았습니다. AWS 글에서는 Full Jitter가 호출 수가 가장 적었지만, 여기서는 Full Jitter의 도착 요청 수가 셋 중 가장 많았습니다. Full Jitter는 대기 시간이 0에 가까운 값도 나올 수 있어서, 서버가 죽어 있는 첫 1초 동안 시도를 더 많이 쓴 것으로 보입니다. 실험 조건(AWS 글은 낙관적 동시성 제어 경합, 이 글은 1초 장애)이 다르면 결과도 달라진다는 뜻이므로, 어떤 지터를 고르느냐보다 **지터를 넣느냐 마느냐**가 훨씬 큰 차이라고 읽는 편이 안전합니다. Decorrelated Jitter는 일부 실행에서 클라이언트 1~2개가 10번을 다 쓰고 실패했습니다.

## 4. 실험 2: 원인이 사라져도 회복하지 못한다

이번에는 요청이 한 번에 몰리는 게 아니라 **꾸준히 들어오는** 상황입니다. 초당 300건이 15초 동안 들어오고, 서버는 초당 400건을 처리할 수 있어 여유가 있습니다. 3초부터 6초까지 3초 동안만 서버의 처리 시간이 25ms에서 100ms로 느려졌다가(처리 능력 초당 100건) 원래대로 돌아옵니다. 클라이언트 타임아웃은 200ms, 시도는 최대 3번입니다.

| 정책 | 서버에 도착한 요청 | 증폭 | 헛처리 | 6초 이후 성공률 | 회복 |
|---|---|---|---|---|---|
| 재시도 없음 | 약 4,500 | 1.00배 | 898~904 | 84.1~84.3% | 해소 약 2초 뒤 |
| 즉시 재시도 | 11,656~11,661 | 2.59배 | 4,042~4,048 | 0.0% | 끝까지 회복 못 함 |
| 지수 백오프(지터 없음) | 11,654~11,661 | 2.59배 | 4,105~4,114 | 0.0% | 끝까지 회복 못 함 |
| 지수 백오프 + Full Jitter | 11,656~11,659 | 2.59배 | 4,086~4,102 | 0.0% | 끝까지 회복 못 함 |

"헛처리"는 서버가 끝까지 처리했지만 클라이언트는 이미 타임아웃으로 떠난 요청 수입니다. 세 번 반복해도 결과는 거의 같았습니다.

### 무슨 일이 벌어졌나

느려진 3초 동안 대기 줄이 200개까지 꽉 찼습니다. 6초에 처리 속도가 돌아왔지만, 줄이 꽉 찬 상태에서는 새로 들어온 요청이 약 0.5초(200개 ÷ 초당 400건)를 기다려야 합니다. 타임아웃은 0.2초이므로 **줄에 선 요청은 전부 타임아웃**됩니다. 서버는 초당 400건을 열심히 처리하지만, 그 결과를 기다리는 클라이언트는 없습니다.

재시도가 없으면 초당 300건만 들어오니, 줄이 초당 100개씩 줄어들어 약 2초 뒤 정상으로 돌아옵니다. 재시도가 있으면 타임아웃된 요청이 다시 들어와 유입이 초당 최대 900건이 됩니다. 처리 능력 400건보다 많으니 줄은 영원히 꽉 차 있고, 성공률은 0%에서 움직이지 않습니다. **원인은 3초 만에 사라졌는데 장애는 관측한 9초 내내 계속됐습니다.** 1장에서 인용한 "원래 문제가 해결된 뒤에도 회복을 늦춘다"는 설명이 그대로 재현된 것입니다.

### 백오프와 지터는 여기서 아무 도움이 안 됐다

눈여겨볼 점은 지수 백오프와 Full Jitter를 넣어도 결과가 즉시 재시도와 같았다는 것입니다. 솔직히 조금은 나아질 줄 알았습니다. 하지만 이유를 따져 보면 당연합니다. 새 요청이 계속 들어오는 서비스에서 백오프는 재시도를 **뒤로 미룰 뿐 없애지 않습니다**. 요청 하나가 3번 시도하는 한, 시간당 서버에 도착하는 총량은 여전히 3배에 가깝습니다.

실험 1에서 지터가 효과를 낸 건 클라이언트 수가 1,000개로 정해져 있었고, 문제가 "같은 시각에 몰림"이었기 때문입니다. 실험 2의 문제는 "총량"입니다. AWS Builders' Library 글도 상한이 있는 지수 백오프의 한계를 짚으면서, 해결책으로 재시도 횟수 제한과 토큰 버킷으로 재시도를 제한하는 방법을 듭니다.

## 5. 재시도 예산: 재시도의 총량에 상한을 둔다

재시도 예산(retry budget)은 "재시도는 전체 요청의 일정 비율까지만"이라는 규칙입니다. 확인한 자료마다 구현은 조금씩 다릅니다.

| 출처 | 방식 |
|---|---|
| Google SRE 책 (Handling Overload) | 요청당 최대 3번 시도. 그리고 클라이언트별로 재시도 비율이 10% 미만일 때만 재시도 |
| Google SRE 책 (Addressing Cascading Failures) | 서버 전체의 재시도 예산. 예: 프로세스당 분당 60번까지만 재시도 |
| AWS Builders' Library | 토큰 버킷으로 재시도를 제한. 토큰이 있는 동안은 재시도하고, 떨어지면 일정 속도로만 재시도 |
| gRPC 재시도 문서 | `retryThrottling` 설정. 실패하면 토큰 1 감소, 성공하면 `tokenRatio`만큼 증가, 토큰이 `maxTokens`의 절반 아래면 재시도 중단 |

SRE 책은 요청당 3번 제한만 있으면 최악의 경우 요청이 3배 가까이 늘지만, 클라이언트별 10% 예산을 더하면 일반적인 경우 1.1배로 줄어든다고 설명합니다.

이 글에서는 가장 단순한 형태로 구현했습니다. 첫 시도마다 토큰이 0.1개씩 쌓이고, 재시도는 토큰 1개를 씁니다. 평균적으로 요청 10건당 재시도 1건까지만 허용됩니다.

```js
class RetryBudget {
  constructor(ratio, maxTokens) {
    this.ratio = ratio;            // 0.1 = 재시도를 전체의 10%까지
    this.maxTokens = maxTokens;    // 잠깐의 실패 몰림을 받아 줄 여유분
    this.tokens = maxTokens;
  }
  onFirstAttempt() {
    this.tokens = Math.min(this.maxTokens, this.tokens + this.ratio);
  }
  tryRetry() {
    if (this.tokens >= 1) { this.tokens -= 1; return true; }
    return false;                  // 예산이 없으면 재시도하지 않고 바로 실패
  }
}
```

예산 객체는 요청마다 만들지 않고, 같은 대상 서비스를 호출하는 **모든 요청이 하나를 함께** 써야 합니다. 실험 2와 같은 조건에서 Full Jitter에 이 예산(비율 0.1, 최대 토큰 30)을 더한 결과입니다.

| 정책 | 서버에 도착한 요청 | 증폭 | 헛처리 | 6초 이후 성공률 | 회복 |
|---|---|---|---|---|---|
| 재시도 없음 | 약 4,500 | 1.00배 | 898~904 | 84.1~84.3% | 해소 약 2초 뒤 |
| Full Jitter(예산 없음) | 11,656~11,659 | 2.59배 | 4,086~4,102 | 0.0% | 끝까지 회복 못 함 |
| Full Jitter + 재시도 예산 10% | 4,679~4,680 | 1.04배 | 1,156~1,160 | 77.2~77.3% | 해소 약 3초 뒤 |

증폭이 2.59배에서 1.04배로 줄었고, 서버는 스스로 회복했습니다. 과부하 동안에는 재시도 약 1,490건이 예산 부족으로 막혔습니다.

숨기지 않고 적어 둘 점도 있습니다. 예산을 써도 **재시도 없음보다 회복이 1초쯤 늦었습니다**. 10%의 재시도가 여전히 부하를 보태기 때문입니다. 그리고 느려진 3초 동안의 성공률은 어떤 정책이든 약 2%로 같았습니다. 재시도 예산은 과부하 중의 실패를 줄여 주는 장치가 아니라, 재시도가 장애를 **연장하지 못하게** 하는 장치입니다.

### 그럼 평소에는 손해가 없을까

재시도를 10%로 묶으면 평소의 이득까지 사라지지 않을까 확인했습니다. 서버는 멀쩡하고 요청의 5%만 무작위로 실패하는 상황에서 초당 300건을 10초 동안 보냈습니다.

| 정책 | 성공률 | 증폭 | 예산으로 막힌 재시도 |
|---|---|---|---|
| 재시도 없음 | 94.8~95.7% | 1.00배 | - |
| Full Jitter(최대 3번 시도) | 99.97~100% | 1.05~1.06배 | - |
| Full Jitter + 재시도 예산 10% | 99.97~100% | 1.05배 | 0건 |

실패율이 5%면 필요한 재시도도 5% 남짓이라 예산 10% 안에 들어갑니다. 예산이 있든 없든 성공률은 같았고, 막힌 재시도는 한 건도 없었습니다. 평소에는 재시도의 이득을 그대로 누리고, 실패가 예산을 넘을 만큼 많아질 때만 제동이 걸립니다.

## 6. 주의할 점과 한계

**재시도해도 되는 요청인지 먼저 확인합니다.** RFC 9110은 같은 요청을 여러 번 보내도 서버에 의도한 효과가 한 번 보낸 것과 같은 메서드를 멱등(idempotent)이라 정의하고, 표준 메서드 중 PUT, DELETE와 안전한 메서드(GET 등)가 여기에 해당한다고 합니다. POST로 결제나 주문을 만드는 요청은 타임아웃이 났더라도 서버에서는 처리됐을 수 있습니다. AWS 글도 부작용이 있는 API는 멱등성을 제공하지 않는 한 재시도하기에 안전하지 않다고 봅니다.

**재시도할 오류와 아닌 오류를 나눕니다.** SRE 책은 영구적인 오류나 잘못된 요청은 재시도해도 성공하지 못하니 재시도하지 말라고 합니다. 입력 값 오류(4xx 대부분)를 재시도하는 건 부하만 늘립니다.

**재시도는 한 계층에서만 합니다.** SRE 책은 거절한 계층의 바로 위 계층에서만 재시도하라고 권합니다. 그러려면 아래 계층이 "과부하이니 재시도하지 말 것"을 구분되는 오류로 알려 줄 수 있어야 합니다.

**서버가 기다리라고 하면 따릅니다.** RFC 9110의 `Retry-After` 헤더는 다음 요청까지 얼마나 기다려야 하는지를 날짜나 초 단위로 알려 줍니다. 503 응답과 함께 오면 서비스를 쓸 수 없을 것으로 예상되는 시간을 뜻합니다. 클라이언트의 백오프 계산보다 이 값을 우선하는 편이 맞습니다.

**서버 쪽 대책도 함께 필요합니다.** 실험 2에서 재시도 없음조차 회복에 2초가 걸린 이유는, 서버가 이미 떠난 클라이언트의 요청을 처리하느라 시간을 썼기 때문입니다. SRE 책은 클라이언트가 포기한 요청을 처리하는 건 인정받지 못할 일을 하는 것이라며, 데드라인을 전달해 그런 요청을 버리는 방법과 과부하에 가까워지면 일부 요청을 버리는 로드 셰딩을 설명합니다. 대기 줄을 타임아웃 안에 처리할 수 있는 길이로 줄이는 것만으로도 상황이 달라집니다.

**이 실험의 한계**도 있습니다. 가짜 서버는 과부하에서도 처리 속도가 일정하지만, 실제 서버는 부하가 커지면 메모리나 커넥션이 바닥나 더 느려지곤 합니다. 클라이언트도 하나의 프로세스라 예산을 완벽하게 공유했지만, 실제로는 앱 서버마다 예산이 따로 있습니다. 숫자 자체보다 정책 사이의 **방향**을 참고하시기 바랍니다.

## 7. 어떤 방법을 고를까

| 상황 | 추천 |
|---|---|
| 지금 재시도가 반복문으로 즉시 다시 호출 | 시도 횟수를 2~3번으로 제한하고 지수 백오프 + 지터부터 적용 |
| 배포·재연결 뒤 요청이 한꺼번에 몰림 | 지터(Full Jitter 등)로 시각을 흩기 |
| 의존 서비스가 느려지면 함께 죽음 | 재시도 예산(전체의 10% 등)으로 총량 제한 |
| 호출 계층이 3단 이상 | 가장 아래 호출의 바로 위 한 곳에서만 재시도 |
| 결제·주문처럼 부작용이 있는 호출 | 멱등성을 보장한 뒤에만 재시도 |
| HTTP 클라이언트·SDK를 쓰는 중 | 직접 만들기 전에 라이브러리의 재시도·스로틀 설정부터 확인 |

마지막 줄을 덧붙이면, AWS 글에 따르면 대부분의 AWS SDK가 지수 백오프와 지터를 재시도 동작으로 지원하고, gRPC는 서비스 설정의 `retryPolicy`와 `retryThrottling`으로 같은 기능을 제공합니다. gRPC는 백오프에 ±20% 지터를 적용한다고 문서에 적혀 있습니다. 쓰는 라이브러리에 이미 있는 기능이라면 직접 구현하는 것보다 설정을 켜는 편이 안전합니다.

## 마무리

- 재시도는 일시적인 실패에는 약이지만, 과부하에는 부하를 몇 배로 키우고 **원인이 사라진 뒤에도 장애를 이어 가게** 합니다.
- 지수 백오프만으로는 재시도가 같은 시각에 몰립니다. **지터**를 넣자 예제에서는 복구 뒤 몰림이 1,000건에서 147~258건으로 줄고 완료 시간이 절반 이하가 됐습니다.
- 하지만 요청이 계속 들어오는 상황에서 백오프와 지터는 **총량을 줄이지 못했습니다**. 예제에서는 즉시 재시도와 똑같이 회복하지 못했습니다.
- **재시도 예산**으로 재시도를 전체의 10%로 묶자 증폭이 2.59배에서 1.04배로 줄고 서버가 회복했습니다. 평소 5% 실패 상황의 성공률에는 영향이 없었습니다.
- 재시도는 한 계층에서만, 멱등한 요청에만, 재시도할 만한 오류에만 합니다.

요청이 한순간에 몰리는 또 다른 사례인 캐시 만료 문제는 [캐시 스탬피드 글](/2026/11/24/cache-stampede-redis/)에서 다뤘습니다. 거기서 쓴 TTL 지터도 이 글의 지터와 같은 생각입니다. 같은 순간에 일어날 일을 무작위로 흩어 놓는 것입니다.
